# 03 — Domain & data model / Dominio y modelo de datos

## Core entities

### User
Represents a human identity. Authentication credentials may live in an external identity provider.

Key fields: `id`, `displayName`, `email`, `locale`, `timezone`, `status`.

### Workspace
Security and collaboration boundary. A workspace normally represents a company, team or personal workspace.

Key fields: `id`, `name`, `slug`, `type`, `status`, `settings`, `createdAt`.

### Membership
Connects a user to a workspace and role/capabilities.

Key fields: `userId`, `workspaceId`, `role`, `capabilities`, `status`.

### Project
Container for coordinated work.

Key fields: `id`, `workspaceId`, `name`, `description`, `status`, `health`, `progressMode`, `progress`, `ownerId`, `startAt`, `dueAt`, `sourceLinks`.

### Milestone
A measurable phase or delivery checkpoint belonging to a project.

### Task
Atomic actionable work item.

Key fields: `id`, `scope`, `workspaceId?`, `ownerUserId?`, `projectId?`, `title`, `description`, `status`, `priority`, `assigneeIds`, `dueAt`, `reminderRules`, `dependencies`, `source`.

### Alert
Attention signal. Alerts may be manually created or generated from rules/integrations.

Key fields: `id`, `workspaceId?`, `ownerUserId?`, `projectId?`, `severity`, `type`, `title`, `message`, `status`, `fingerprint`, `source`, `firstSeenAt`, `lastSeenAt`, `resolvedAt`.

### Decision
Durable record of a product/project decision.

Key fields: `id`, `workspaceId`, `projectId?`, `title`, `context`, `decision`, `status`, `supersedesId?`, `madeBy`, `madeAt`.

Decision lifecycle states are `active`, `superseded` and `reversed`. New decisions start as `active`. A decision may transition from `active` to exactly one terminal lifecycle state:

- `superseded`: another decision explicitly replaces it;
- `reversed`: the decision is withdrawn without a replacement.

A decision is workspace-only. When `projectId` is present, the referenced project must resolve inside the same authenticated workspace. When `supersedesId` is present, the referenced decision must also resolve inside the same workspace and still be `active`. A replacement inherits the previous decision's `projectId` when no project is explicitly supplied. If both decisions declare a project, the projects must match.

Lifecycle transitions emit server-authored Timeline events. A reversal requires a human-readable reason in the mutation request; the reason is retained in the audit event rather than mutating the original decision text.

### TimelineEvent
Immutable or append-oriented normalized event representing meaningful activity.

### IntegrationConnection
Normalized configuration reference for a connector. The core model currently supports provider `github` and status `active | disabled | error`. A connection is workspace-scoped. Secrets are never stored as plain fields in the domain document; `secretRef`, when present in a future connection slice, points to an external/runtime secret store.

Key fields: `id`, `scope`, `provider`, `displayName`, `status`, `secretRef?`, `createdAt`, `updatedAt`.

### ExternalResource
Normalized reference to an object owned by an external provider. Provider-specific response payloads do not become core domain types.

Supported normalized kinds start with:

- `repository`
- `pull_request`
- `issue`
- `workflow`
- `release`

Key fields: `id`, `scope`, `provider`, `kind`, `externalId`, `displayName`, `url`, `projectId?`, `connectionId?`, `metadata`, `createdAt`, `updatedAt`.

The first Phase 4 slice stores GitHub repository links as workspace-only `ExternalResource` records. `externalId` is a canonical case-insensitive `owner/repository` key. The GitHub URL is built server-side from validated owner/repository components; callers cannot persist arbitrary upstream URLs. When `projectId` is present for a repository link, the project must exist in the exact same workspace scope.

A workspace may link a canonical repository at most once. Link/unlink mutations are transactionally audited through `audit_outbox` so resource state and its audit event commit atomically.

## Scope model

Every actionable object must have one explicit visibility scope:

- `private`: visible only to the owning user unless explicitly shared in a future feature.
- `workspace`: visible according to workspace permissions.
- `system`: generated by integrations/rules and visible according to the owning workspace/user scope.

Integration connections and external resources are workspace-only in the current implementation. Provider credentials never define authorization scope; the authenticated Command Center session does.

## Project progress

Supported modes:

- `manual`: explicit percentage with audit trail.
- `milestones`: weighted milestone completion.
- `tasks`: weighted task completion.
- `external`: normalized metric from a source adapter.

The UI must expose the progress source and confidence.

## Alert lifecycle

`open -> acknowledged -> resolved`

Additional terminal state: `dismissed` where policy allows. Reappearing integration alerts use a fingerprint to avoid duplicate noise.

## Data isolation

Every database query for workspace-owned data must include the workspace boundary at repository/service level. UI filtering is not a security boundary.

Private objects use `ownerUserId` as the mandatory boundary and must not become visible to workspace admins solely because of their role.

External resources include the workspace scope in uniqueness, reads, deletes and project-reference validation. A raw external provider ID or resource ID is never sufficient for authorization.

## Auditability

Important changes to permissions, alerts, decisions, integrations and project progress should emit timeline/audit events with actor, timestamp and source.

Initial GitHub repository-link events:

- `integration.github.repository_linked`
- `integration.github.repository_unlinked`
